# CLAUDE.md

Guidance for AI agents working in this repo. Read [README.md](README.md) first for what the project is and where it stands; this file covers what is not obvious from the code and the traps found during reverse engineering. The sibling project [OddworldMap](https://github.com/MagogCartel/OddworldMap) is the model for where this is headed — its viewer is data-driven and most of it will be reusable once Metal Slug data is extracted.

## Where the data lives (Metal Slug X, NTSC-U, SLUS-012.12)

- Standard ISO9660 disc, raw 2352-byte Mode 2 sectors; `tools/disc.py` reads it with no game-specific logic. The disc has a **directory tree** (`\ST01`..`\ST06` with `_1`/`_2`/`_3` sub-stage folders, plus `\PL`, `\STD`, `\LD`, `\ANG`, `\ART`) — 354 files in all. `disc.py` keys them by basename, which is safe only because no basename repeats across directories; check that again before trusting a name if the reader ever handles a second disc.
- `X<n>.BIN` is a mission's **base artwork**, nothing else: a chain of TIM records covering 99% of the file. `X1`, `X3`, `X4` are missions; `X21/X22/X23`, `X51/X52/X53`, `X61/X62/X63` are sub-stages of multi-part missions.
- `X<n>_<nn>.BIN` are the per-mission section files, 150 of them. Most (124) are more TIM artwork; 26 carry data. Their first bytes identify the kind: `22 03 00 00` a tile list, `23 00 00 00` and `00 00 55 00` unidentified tables, `70 51 45 53` (`pQES`) sequence data, and `27 bd ff d8`-style MIPS prologues mark **code overlays** (`X3_0801`, `X61_000`) — the game streams executable code per section, so behaviour is not all in the main executable.
- `X09.BIN` and `X801.BIN` are **streamed media, not art** — both start with an audio sync header, entropy alternating ~0.5 and ~7.9 bits/byte (interleaved XA-ADPCM and/or MDEC video). Do not mistake them for sprite banks.
- `SLUS_012.12` is the game executable (622 KB MIPS) — the only structural ground truth, since no decompilation of this port exists (unlike Oddworld's alive_reversing).

## Format gotchas (established so far)

- Artwork is **raw PS1 TIM**, no custom compression, and each record carries its own VRAM destination — a mission's art is reconstructed by replaying those uploads into a 1024x512 halfword VRAM (`tools/vram.py`), which is the state everything else addresses.
- A section's **number is a path through the stage**, not a plain counter: `04` opens the step that `040`..`043` scroll through, so sorting the numbers as text gives the order the player reaches them (`load_order`). That order is the mission's streaming order, and replaying it (`stream`) is what makes the art come out right — loading every file at once, or only the section's own, both give a coherent-looking mosaic of the wrong pictures.
- A tilemap is **not** drawn at the point its own file loads. `X1_00.BIN` holds most of mission 1's tilemaps while the art streams in behind it, so its later pieces want art from `X1_02`/`X1_041`/`X1_081`. Nothing records which state a piece belongs to, so `tools/render.py` measures it: tiles cut from one picture join seamlessly, so the state with the smallest colour break across a piece's internal seams (`roughness`) is the state it was drawn under. Guard the comparison with the seam *count* — a page nothing has written to joins perfectly with nothing.
- **The TIM magic word is optional.** Only the first record in a file tends to carry `10 00 00 00`; the rest begin at the flag word. A scanner that requires the magic silently stops after one record — this hid 13 of X1.BIN's 17 pages at first. Validate records by their block lengths (`12 + w*h*2 == bnum`) instead.
- `08 00 00 00` at the head of a file is **not a container kind** — it is a TIM flag word (4-bit, has CLUT), and the `{count, w, h, cell}` that seems to follow is the CLUT block's own header. `_VHIECLE.BIN` and `STD0n.BIN` are plain TIM chains like the mission art, and a pass that read them as a sprite-bank format invented a frame table that does not exist.
- The **sprite banks come off whole**: `STD00`-`STD04` are the four playable characters, `MUM01`-`MUM04` and `FAT01`-`FAT04` their mummified and fat forms, `_VHIECLE.BIN` the vehicles. A page is a sheet of every frame the game animates. Cutting the individual frames out needs `\PL\PAT*.BIN`, which holds no art at all — 4-byte units that read as `(dx, dy, u16 index)` sprite assembly, with the index-to-pixels mapping still unidentified.
- Pages are 256x256 4-bit **atlases**, not finished pictures: a page rendered straight from its TIM looks like scrambled fragments, and that is correct.
- A page's tiles each want a different palette, so a page carries a bank of 6-16 CLUTs and the assignment lives in a **tile list** (`tools/tilelist.py`): 8-byte records, 256 per page, in raster order with destination equal to source. Read as drawing, a list just repaints its pages; read as a table, record *i* is the definition of tile *i* — source page, position in it, palette — which is what the tilemap indexes. It is also the only route to true colours; a raw TIM read gives shapes under one palette's cast.
- **VRAM is time-dependent.** Section files upload over each other during play, so loading a mission's whole file set at once corrupts pages. `stream` replays the load order and hands each file the memory it finds; `stage` fills only the blocks nothing has written yet, so a list reaching for art streamed in later still resolves without overwriting what is already correct.
- The **stage layout** is the `23 00 00 00` section (`tools/tilemap.py`), which usually follows the tile list in the same file: an 8-byte header of `kind, width, height, 16, 16` then a row-major grid of u16 tile indices into the tile list, 0 meaning empty. Sizes are per section (X1_00 is 34x16 tiles = 544x256px, X22_00 is 20x26). `tools/render_map.py` draws one end to end; X3_00 comes out with no empty cells at all.
- The viewer lives in `public/` (dependency-free ES modules, no build step; `js/main.js` boots, `js/state.js` holds shared state and the world transforms, and modules talk through the `emit`/`on` pair rather than importing each other both ways) and is built by `tools/build_map.py`, which renders every piece and emits `map_data_msx.json`. `public/pieces/msx/**` and that JSON are generated **and committed** — regenerate them from the disc, never hand-edit.
- The canvas holds a **map of live pointers** rather than one drag, because two fingers have to pinch. Two traps follow: `setPointerCapture` on a touch pointer keeps the browser from ever seeing the pinch that ends a page zoom, so it is skipped while `visualViewport.scale` says one is in effect (`touch-action` relaxes to `pinch-zoom` to match); and lifting one finger of a pinch must hand the gesture back to panning from where the other finger is, or the map jumps.
- **A stage does not always run sideways.** Mission 2's pyramid interior stacks: `X23_00` offers 33 top-to-bottom joins and *no* left-to-right one, and `X22_00` 7 against 3. Every other section is the other way round. `orientation` counts the joins each direction affords and picks the axis; sideways is the default and must be beaten by `UPRIGHT` (2x), because a section of narrow same-width chunks throws off vertical matches whichever way it runs — `X4_004` scores 31 against 24 and is a street.
- **Piece order is file order, and the cross-axis size groups the lanes.** Pieces sharing a height (sideways) or a width (upright) are one lane and run in file order along the axis; lanes are ordered by total extent, the longest being the ground the player covers. Whether two neighbours really meet is measured — the builder butts them together only when their facing edges match (`seam` under `JOIN`) and leaves a marked break when they do not. Order within a lane stays file order rather than the cheapest seam: a section's repeated wall chunks all match each other equally well (nine of `X23_00`'s tie at 3.99), so the seams say a lane exists without saying how it is sequenced.
- A run of three or more same-shaped tilemaps that agree on most of their cells is **one animated object stored as its frames**, not three pieces of stage — `X4_051` is ~18 four-frame props, and reading them as stage was most of what made mission 4 look like a heap. Distinguish by cell agreement (`FRAMES`), not by seam cost: seams are unreliable on low-contrast edges.
- The tile-list header carries a **tile size** at bytes 6-7 that is 16x16 in every mission file but 32x32 in the `WAIT_*.BIN` loading screens, and the kind word's **top byte carries flags** (`23 00 00 c0` is still a tilemap) — mask it off before comparing, or five pieces go missing.
- Which *section files* a mission plays in, and their scroll extents, is **still open**; so are object spawns. The executable carries a full ISO path for nearly every other asset (`\ST01\ST01.BIN;1`, `\PL\PAT1A.BIN;1`, `\ANG\M1\MISS01.BIN;1`) and **not one** for an `X<n>_<nn>.BIN`, nor a format string to build one — so the section files are reached by something else, and the absence is evidence rather than an oversight.
- The executable carries a **135-entry asset manifest** at `0x800841c4`, sixteen bytes of `{path, load address, lba, size}` with the last two filled in at runtime (`tools/manifest.py`). The load address is the key to everything else: it says where a file ends up, so an overlay can be disassembled, and it groups the files that share a slot — `ST02A/B/C` land on `ENEMY.BIN`'s address, the `ST0n.BIN` files all land on one per-stage slot.
- The whole **`ST*` family is MIPS code**, not a data container: `ST01`, `ST02` and `ST02A/B/C`, `ST03`/`ST03A`, `ST04`, `ST05`/`ST05A/B/C`, `ST06`/`ST06A/B/C` and `ENEMY.BIN`. Each is a per-sub-stage overlay of object behaviour that installs handlers by writing a function pointer into the actor at `*(0x800c9a98)` — the same global the executable's sprite routine at `0x800436e8` uses. `ST02.BIN` opens with a header of pointers just past itself, which is why it looked like a table.
- To decide whether a file is code, and to confirm a load address at the same time: count `addiu $sp, $sp, -N` prologues, then measure how many of the file's own `jal` targets land exactly on one (`tools/manifest.py --code`). Every `ST*` file scores 60-92% at its manifest address and 0-2% at a deliberately wrong one; `_VHIECLE.BIN` and `PAT1A.BIN`, which really are sprite banks, score zero. Do not judge these files by byte histograms — a previous pass read the 1/2/4/8/16/128 spike as 4-bit pixel edges when it is MIPS opcode and register fields.
- The **actor system**, recovered by running the code rather than reading it: `0x80014f24` allocates one — `a0` flags, `a1` parent (0 takes the current actor), `a2` the free count it insists on — popping the free list at `*(0x800c9a94)`, decrementing the count at `0x800d41fc`, and handing back a dummy at `0x800d40b0` when the pool is empty. The caller fills the new actor in afterwards, so a trap on this address catches every creation but not yet its position.
- `lui r, 0x800d` followed by a *negative* offset lands in the 0x800c range, not 0x800d. An earlier pass read `lw $v1, -25960($s0)` after `lui $s0, 0x800d` as `0x800d9a98`; it is `0x800c9a98`. The emulator caught this immediately — the routine wrote nothing until the address was fixed — which is the argument for running code over eyeballing it.
- Running the code needs a handful of stubs and nothing else (`tools/machine.py`). The **kernel** is reached the way every PlayStation title reaches it, by `jr` to 0xA0/0xB0/0xC0 with the function number in `$t1`, plus `syscall` for critical sections; only the memory and string calls do real work, and `A(0x2b)` memset is the one the actor pool cannot start without. The **disc** needs no emulation — the loader at `0x8001db64` takes a manifest entry, so a trap there reads the path out of memory and drops that file at the address the entry names, which also settles which overlay is resident in an arena several files share. The **actor pool** initialises by calling `0x80014cd0`: 119 actors of 332 bytes from `0x800ca64c`, free list at `*(0x800c9a94)`, count at `0x800d41fc`.
- Getting from the entry point to the main loop takes four more things, each of which announces itself as a hang or a bad opcode. `GPUSTAT` (`0x1F801814`) must read back its ready bits or the drawing code waits forever on a chip that is not there. The **geometry coprocessor** needs a register file but no arithmetic — it only ever feeds drawing, and placement code reads coordinates out of memory. The **disc driver** polls hardware and times out in bounded loops over and over, so its library entries (`0x80061cf8`, `0x80071354`, `0x800715c4`) answer success instead. And **crt0 is not worth running**: its static-initialiser loop returns through a register the loop itself clobbers, so clear the zero-init range `0x800c9a50`..`0x800fa6b0`, set `$gp` to `0x80010000`, plant a stack and call `main` at `0x8001255c` directly.
- **The executable's image lies about the region from `0x8009c0e8`.** `ENEMY.BIN` and `ST02A/B/C` load there, so whatever the static exe holds at those addresses never executes. An earlier pass disassembled `0x800a47e0` out of the exe image, found coherent MIPS, and concluded mission 2's handler lived in the executable; under emulation the file load overwrites it. Disassemble that range only after deciding what is resident.
- Guard the interpreter against **jumps to null**: zeroed memory decodes as `nop`, so a call through an uninitialised pointer walks up through low RAM and reaches a kernel vector, arriving as a plausible-looking BIOS call with a garbage function number instead of an error.
- So **there are no spawn tables**. Object placement in this game is compiled code: the stage sections carry artwork, tile lists and tilemaps, and everything that moves is an overlay calling executable routines. Extracting placements would mean emulating the overlays or reading a few hundred KB of disassembly per mission, not decoding a struct.
- `0x80082be0` is a `{mission, sub-stage, ?, ?}` to handler-pointer table, nine entries and a `-1` terminator, whose targets land in the overlay arena — the per-sub-stage entry points. The arena is shared and overlapping (`ST01` alone spans `0x800fa6b0`..`0x8013dbc4`), so a pointer cannot be attributed to a file by range alone; check it against that file's own prologues instead.
- `X4_000`/`X4_040` are **not** part of that family despite opening the same way: they use 19 distinct byte values against ~97% zero, concentrated at two offsets of a 112- or 144-byte stride, which is a sparse struct array rather than pixels.
- The **executable holds a script VM**: `0x80084ec8` is a 12-entry dispatch table whose handlers read a halfword operand from `$a0`, index a table whose address lives in a variable, and return `$a0 + 2`. So behaviour is bytecode with a runtime-chosen opcode set — which is what `X4_050.BIN` is, a header of pointers into its own body once loaded at ~`0x80129600`.
- **Section code overlays are one object's behaviour, not a stage loader.** `X61_000.BIN` loads at `0x80130000` and `X3_0801.BIN` at `0x80168000` (recovered from where their own `jal`s point, which `tools/mips.py --base` then takes). X61_000 calls one exe routine ten times with sprite id 282 and nothing resembling a spawn. Do not expect the stage format to be parsed here.
- The 16-byte record `(x1, y1, x2, y2, kind, flag, power, -1)` is an **object-local box**, seen both in `X4_001.BIN` and at `0x80085700` in the executable. Its coordinates straddle the origin, so it is a hitbox and never a placement.
- Ruled out for spawns, with the measurement: the tilemaps carry no out-of-range cells that could mark one (0 of 55,658 across every piece); only 14 section files in the whole game are neither art nor stage, and seven of the twelve sub-stages have none at all.
- `MISS<nn>.BIN` and `MI<nn>STD/MI<nn>_00.BIN` run to twenty each, and the game has six missions — they are **Combat School**, not the main game (`CSCHOOL.BIN`, `CSC*.BIN` are its shell). None of them holds a tilemap, so the earlier reading of them as main-mission overlays was wrong; do not spend the spawn hunt there.
- `ENEMY.BIN` holds 36-byte records and embeds the same `00 00 55 00` marker the Combat School headers open with, so that marker is a chunk kind shared across files rather than a file signature. What follows it is a table of round numbers (100/300/500/700, or 5000/7000 in `X3_080`) in groups of six — a difficulty or score table's shape, not coordinates.
- Where spawns are **not**: the stage sections are art, tile lists and tilemaps and almost nothing else (`census` the files and the leftovers are a few hundred bytes); the executable holds no `0x322` constant at all, so it does not parse section files itself; `70 51 45 53` (`pQES`) blobs are PS1 sequence *music*. The live leads are the `X<n>_0N0.BIN` files that open each group — `X4_001` is object-local hitboxes (`-16,0,32,36` style boxes), `X4_050` is a table of `0x8012xxxx` pointers into its own body, and `X4_000`/`X4_040` are ~97% zero with one u16 set every 112 or 144 bytes.
- Tilemaps and tile lists also appear **after** a file's leading TIM art, so a chunk walk that starts at offset 0 and stops at the first non-chunk misses most of them: scanning the whole file finds 277 pieces across 24 section files, against 128 from walking alone. Accepting a chunk skips its payload, which is what keeps tile data from matching as a chunk itself; a tile list is further checked by its first records placing 16x16 tiles on multiples of 16.
- A tilemap usually follows the tile list its indices mean, but some files (`X21_00`, `X52_00`, `X4_042`, `X4_074`) put **every tilemap first and the list after them**, so a map with no list before it takes the next one. A file with no list at all (`X3_12`) is skipped — its indices belong to a list held elsewhere.
- Multi-part missions share structure across their sub-stage files (`X51/X52/X53`) — diffing sub-stages of one mission is the fastest way into an unknown table.

## Conventions (inherited from the sibling project)

- One concern per commit; split bundled diffs before committing.
- A user-facing or behaviour change ships its docs in the same commit — update README.md / this file as part of the same concern, not a follow-up.
- Prose files (README, docs, this file) are never manually line-wrapped — let lines run long.
- Code comments — default to none. A comment earns its place only by recording a durable *why* the code can't show: an invariant, a constraint, a non-obvious trade-off. Keep them generic enough that a routine change doesn't force a comment edit — put a per-item note *inline on the item*, never in a doc-comment that re-describes a set's members (that rots the moment you add one). Don't name consumers or other modules ("used by X", "the way the sibling project does"); don't narrate history ("was previously…"); don't restate a constant's value or units. Comment footprint matches code footprint. An absent comment never goes stale.
- No game owns unsuffixed defaults: everything game-specific carries its prefix (`msx`, later `ms1`/`ms2`) in files, identifiers and paths. Do not reintroduce unsuffixed names for Metal Slug X just because it came first.
- Tooling is dependency-free Python 3 (standard library only); `tools/png.py` is a minimal writer rather than a Pillow dependency.
